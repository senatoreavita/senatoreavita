# Bankable business plan — generation & verification spec (pro-memoria)

**Status:** design (2026-11-25). Scope: **Phase 1 (Lender / bankable plan)** + **Phase 3
(cited market research)**. The Equity plan (Phase 2) is **deferred by decision** — see §0b.
Source prompts: `bankable_business_plan_prompt.md` (Phase 1), `equity_investor_business_plan_prompt.md` (reference).

---

## 0. Summary

Turn the engine's deterministic financial model into a **credit-committee-grade business
plan**, written section by section by AI that **may never invent a number, a customer, a
source, or a figure**. The engine already computes ~90% of the required financial KPIs
(DSCR, CFADS, ICR, leverage, liquidity, NPV/IRR, statements, scenarios, cap table). The
build is therefore **not "wire up a prompt"** — it is the **grounding + per-section
generation + verification** system that makes the bankable prompt's Rule #1 ("numbers come
from the model") actually true, plus a **founder-input intake** for the sections the model
cannot contain (market, competition, team, security, ESG). It renders in the **Lender skin**
(Direction B) already built.

## 0b. Why the Equity plan is deferred (recorded decision)

The equity/IC-memo build is **not scheduled**. Rationale: StartUPlan's SME users fund
mostly via **loans + grants**, not priced equity; the sections that make an investor memo
credible (traction, cohorts, cap-table/dilution waterfalls, MOIC/IRR, sourced exit comps)
need modelling + founder data the tool can't reliably supply, and auto-generating them is a
**credibility liability**. The **PPTX pitch deck** already serves the early-investor conversation.

**Consequence (done):** the user-facing **Investor/Lender PDF toggle was removed** — there is
one business-plan PDF, the **bankable (Lender) plan**. The engine *keeps* its two-skin
capability (defaults to the Lender/institutional skin), so an investor-styled PDF can be
re-surfaced later without rework; it is simply not offered in the UI today.

## 1. Non-negotiables (from the prompt, enforced as code)

1. **Every number traces to the model.** The AI is handed a typed *facts* object (pre-formatted
   strings) and forbidden to introduce a figure not in it. A post-generation checker flags any.
2. **No invented market/competitor/customer facts.** Those come from founder input or the
   Phase-3 research tier, each carrying **value · unit · source · date** — never model memory.
3. **Fail-closed to the deterministic draft.** A missing key / AI error degrades a section to
   its template draft; the document always builds.
4. **Missing inputs are surfaced, never filled.** Absent founder data → the section is stubbed
   and listed in **Open Items**, exactly as the prompt requires.
5. **Consistency:** one KPI, one value, everywhere (checked).

## 3. Engine fact inventory & the gap

**Already computed** (`core/engine/ratios.py`, `compute.py`, `funding.py`, `cap_table.py`):
DSCR (series) · CFADS · ICR (EBIT/EBITDA/cash) · net debt / EBITDA · gearing · current & quick
ratios · NPV · IRR · ROI · payback · linked P&L/BS/CF · scenarios/Monte-Carlo · funding & S&U ·
cap table · min cash / funding gap · break-even · CAGR · margins.

**Gap (small):** **LLCR / PLCR** are stubbed `const(None)` ("v2") — project-finance PV-over-loan/project-life
metrics, **optional** (needed only for project-finance deals, not ordinary SME term loans). Build them
only if/when a project-finance use case appears.

## 4. Architecture

```
engine ComputeResult + ratios + cap table
        │  assemble →
   FactsContract (typed, pre-formatted strings; the ONLY numbers the AI may use)
        │                         FounderInputs (market/competition/team/security/ESG,
        │                                        each value·unit·source·date; absent → stub)
        ▼
   per-section generators  (one AI call per section, minimal relevant context + that
   section's rules; deterministic draft is the fallback — already exists in narrative.py)
        │  → section JSON
        ▼
   Verifier (quality gate as code)  ── PASS/FAIL + Open Items
        │
        ▼
   Renderer (Lender skin / Direction B) → PDF  (+ chart pack)
```

- **Per-section, not one mega-prompt** — safer (small scoped prompts hallucinate far less),
  cheaper and **metered** (we ship AI-usage logging), parallelisable, and robust (a failed
  section degrades to its template draft).
- **Grounding** — facts passed as strings; system prompt forbids new numbers; prompt-cache the
  shared rules; a per-plan **token budget**.

## 5. Verification layer (the "verified system")

Implement the bankable prompt's **§10 Quality Gate as code**, run before the PDF ships:

- **Number reconciliation** — every figure in the prose appears in the FactsContract (flag strays).
- **Section presence** — all required Lender sections present.
- **Consistency** — same KPI = same value across Exec Summary / body / charts.
- **Reconciliations** — Sources = Uses; staff cost = headcount × salary × on-costs; capacity ≥ modelled volume.
- **Repayment sentence** present with the DSCR values; **min DSCR (base & downside)** identical everywhere.
- **Open Items** list complete (every stub / `[ASSUMPTION — to confirm]` / missing doc).
- Output a recorded **PASS/FAIL report**; a plan failing a **critical** check is marked *draft*,
  not "bankable".

## 6. Founder-input intake (the non-model sections)

Extend the existing extract/guided flow with a **bankable intake** that collects the §2/3/4/5/6/7/13/14
inputs with the prompt's discipline (**value · unit · source · date**). Anything not provided →
the section is **stubbed + listed in Open Items**, never fabricated. This is the single biggest
*new* user-facing piece and gates how "complete" a plan can be.

## 7. Charts (bankable §8 — mandatory 1–4)

All computable from the engine today:
1. **DSCR profile vs covenant** (series ✓) · 2. **CFADS vs debt service** (✓) ·
3. **Sources & Uses** (✓) · 4. **Tornado** (sensitivities ✓). Optional: debt profile, cumulative
cash / funding gap, EBITDA bridge. Rendered in the Lender skin's chart language (`charts.py`).

## 8. Phase 3 — market research as a separate, opt-in feature

A **distinct feature**, not part of the base plan. It activates **only when the founder provides
no market research** of their own (§4/§5 left empty), and never overrides founder-supplied data.

- **Trigger:** founder opts in **and** has supplied no market/competition inputs → the feature
  runs; otherwise it does nothing.
- **Grounded web search** → candidate facts (market size & growth, competitors, price evidence).
- **Verify every source** — fetch each one, confirm the figure is actually present; **drop any
  claim whose source can't be verified**. Never a model-recalled "reference".
- **Output:** a short, sober **summary** of what serious sources say, with **the source links in
  footnotes** (each fact: value · unit · source URL · date). It reads as *"according to [source],
  the market is …"* — clearly attributed, never presented as the founder's own primary research.
- **Gated** (cost + abuse) and **metered**. Fail-open: if nothing verifiable is found, the section
  stays a founder stub + Open Item, rather than inventing anything.

## 9. Safety / efficiency / professionalism — how each is met

- **Safe:** grounding + number-reconciliation post-check + fail-closed deterministic fallback +
  no invented sources + no PII to the LLM.
- **Efficient AI:** per-section minimal context, structured JSON out, prompt-cached rules,
  per-plan token budget, parallel generation, metering (already shipped).
- **Professional code:** clean contract (facts → generators → verifier → renderer), typed, each
  generator independently tested, no hard-coded numbers, deterministic drafts throughout.
- **Professional plan:** the bankable section/KPI/chart structure, Lender skin, quality gate
  standing behind the word "bankable".

## 10. Build sequence (Phase 1)

1. **FactsContract** — assemble a typed facts object from `ComputeResult` + `ratios` + `cap_table`
   + funding/S&U, every number pre-formatted. (Foundation for grounding + verification.)
2. **Section generators** — one per bankable section, grounded; reuse `narrative.py` drafts as the
   deterministic fallback; route through `core.ai.llm` (metered). Start with the engine-driven
   sections (1, 8, 9, 10, 11, 12).
3. **Verifier** — the §5 quality gate as code; emits PASS/FAIL + Open Items.
4. **Founder intake** — bankable input collection for §2/3/4/5/6/7/13/14; stubs + Open Items.
5. **Renderer** — Lender skin (Direction B) extended to the 14-section structure + charts 1–4.
6. **Wire** — a "Bankable plan" output behind the Lender variant; metered; gated by tier.
7. *(Phase 3)* cited-research tier for §4/§5.

**First slice:** steps 1–3 over the **engine-driven sections** — proves grounding + per-section
generation + verification end-to-end before the intake and full section set.
