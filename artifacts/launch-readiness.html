Spec — plan schema-version migration path

◆ So you can evolve the engine without orphaning saved plans

Where it stands today: every saved plan's inputs are stamped schema_version: 1 on write (planStore.ts), but loadPlans never reads that column back, and PlanInput is extra="forbid". So a breaking input-schema change would silently drop unknown fields — or fail validation — on plans saved by the old build. The stamp is a hook with nothing on the other end. Not a beta blocker (few testers, disposable data); a public-launch requirement, because real users' stored plans must survive engine changes.

The build (small, well-scoped):

  1. One source of truth — CURRENT_SCHEMA_VERSION defined once (shared by the engine input schema and the web persistence), replacing the hard-coded 1 in planStore.
  2. A migrator registry — MIGRATIONS[n]: (inputs) ⇒ inputs, each a pure, additive step that upgrades a plan from version n to n+1 (add a defaulted field, rename a key, re-shape a sub-object).
  3. Version-aware load — on read: take the row's schema_version, run every migrator in sequence from that version up to CURRENT, then deserialize into PlanInput. An unknown/newer version fails loudly, never silently.
  4. Version-aware save — stamp CURRENT_SCHEMA_VERSION (not a literal 1) on every write.
  5. A fixtures test — one saved-plan JSON fixture per historical version; the test asserts each migrates + deserializes green. This is what makes every future schema change safe to ship.

Rules: migrators are pure and forward-only; never mutate stored rows in place — migrate on read, re-stamp on the next save. The engine's output render contract is already versioned (render_dto.py); this closes the matching gap on the input side. Effort ≈ ½–1 day. Deadline: before the first real user stores a plan you can't afford to lose.
