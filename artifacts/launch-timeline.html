Containerise now, iterate freely — the answer to "what if I deploy then still have to change things?" Cloud Run is revision-based: you build an image, ship a revision, and every later code change is just a rebuild → new revision (one-step rollout, one-step rollback). So preparing the container before the exports/dialogs are 100% is not a problem — it's the normal, recommended way to de-risk, and it lets real people start playing while you keep fixing. What you do once, and want right the first time, is the write-once, outward-facing set: the GCP project, domain/DNS, Stripe live keys, the legal entity. Code — engine logic, export fixes, dialog tweaks — redeploys cheaply on top. The real long pole, the business bank account, only gates live payments, not the private beta (which stays in Stripe test mode), so it no longer blocks letting people in.
What a private beta needs (far less than a public launch): deployed + reachable, auth working, RLS isolation verified on prod, the LLM keys set with spend caps, backups on, and invite-only access — payments stay in test mode, and legal docs / monitoring dashboards / SEO can follow. Aim: deploy wk 8 → invite-only beta ~wk 9 (≈30 Nov) → gather feedback + fix through wk 10 → public launch 15 Dec (live keys, go/no-go, monitoring) as a formality.
